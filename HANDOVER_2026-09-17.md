## The next major issue: #26, the R/2.1 GCM pin

This is the highest-severity open item because it is **a live published product that is wrong
in two independent ways**, and the notebook serves it as Future Projections.

`R/2.1_create_monthly_haz_tables.R:189-191` pins 5 of 18 GCMs. The pin is unconditional and
sits outside every section guard, so no `SKIP_*` flag avoids it. Consequences, measured against
the live parquet rather than inferred:

- The published file is **a mixture of ensemble sizes**: 87% of rows at 18 members, 10% at 5,
  2% at 13, and NDD is **wholly 5-member with every anomaly NaN**. Nothing in the file or the
  notebook signals this. A 17th/83rd percentile over a 5-point sample is not a quantile.
- The same filter drops **every historic folder**, because `"historical"` is not in the GCM
  list. Section 2.5 then reads the baseline off disk from an older code path.
- `:186` collapses all 18 historic folders to the single path `historic_historic_historic`,
  and `:224` is skip-if-exists. So removing the pin **alone** silently makes one arbitrary GCM
  the ensemble baseline. The filter and the naming must be fixed together.
- The anomaly baseline appears to resolve to **1981-2014** while the published key is labelled
  `baseline=1995-2014`. Evidenced three ways in the issue, including that the implied baseline
  is constant across years and does not match the 1995-2014 means.

**The design is already decided.** Pete's call: both baseline windows stay supported, because
external users need the second one, and **the baseline window must appear in file and folder
names** rather than collapsing to `historic`. Proposed shape, in the issue thread:

- `R21_BASELINES` environment variable, default `1995-2014`, full product `1995-2014,1981-2014`.
- Historic folders parsed per GCM as `historic_<GCM>_<window>`, nothing collapsed.
- Output names carry the window: `..._<period>_anomaly-<window>_...`.
- Drop the hardcoded `all_baseline_names` and the `unique(timeframe)[1]` baseline lookup.
- Publish loops over windows, keyed `period=<p>/baseline=<w>`, gated on an 18-GCM check.
- `R21_GCMS`, defaulting to all 18, and the membership stamped into the sidecar metadata.

Useful facts before starting: the ID store holds all 18 GCMs for **both** `_1981_2014` and
`_1995_2014`, so the second window is regenerable rather than frozen. The 2025-11 published
`period=1981-2014` object was itself a genuine 18-GCM product. And atlas_notebooks reads only
`baseline=1995-2014`, 17 references, so the notebook is unaffected by which window lands first.
Budget generously: §3.4 alone is about 9 hours per timeframe, and two baselines roughly doubles
the anomaly, ensemble and trends stages.

## Conventions this session earned the hard way

- **A clean exit is not a clean run.** R/3 returned exit 0 for months while every crop × usd
  multiply failed. Check `failed_*.txt`, `skipped_*.txt`, per-variable elapsed times, and output
  mtimes against the run start.
- **Never guard on a label string.** `variable != "ha"` broke silently when `ha_name` became
  `"harv-area_ha"`, sending livestock down a branch with a NULL raster. Branch on the objects
  actually supplied.
- **Gates need row populations, not one bound.** The publish gate blocked a correct product
  twice: once on a crop whose national reference is sub-dollar, once on `generic-crop`, which
  has no reference by design. Split material, immaterial and unmatched, and print with
  `signif()` — `round()` displayed 0.4 as `0` and sent the diagnosis the wrong way for a round trip.
- **Test the tidy explanation before dispatching a day-long job.** Two plausible theories about
  the intld divergence were wrong, and checking them locally cost minutes.
- **This repository is public.** No internal addresses, hostnames or mount identifiers in
  tracked files, including when quoting them to recommend their removal.
